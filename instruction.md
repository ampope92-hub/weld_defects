We do robotic welding for structural fabricators and every joint gets an ultrasonic inspection after, which is slow and expensive. I want to flag the joints worth inspecting straight off the process data. /app/data/train.csv is nine thousand welds where the inspector recorded what they found, defect is none if the weld was clean, otherwise its the defect type. /app/data/test_features.csv is a batch we have since had fully inspected but I've held the findings back. There is a README in /app/data explaining the process columns.

Our cell software is Rust so this has to live there. /app/predictor is a Cargo project with smartcore and csv already wired into Cargo.toml, fill in src/main.rs so that running it reads both CSVs, fits whatever model you think will hold up, and writes /app/predictions.csv with exactly two columns, weld_id and defect, one row for every weld_id in test_features.csv, header included, any order. defect is your single best call for that weld, spelled exactly as in the training column. The box is offline, the crates already in Cargo.toml are cached locally at the Cargo.lock versions so builds work, but you cant pull new ones in. It has to work from a clean build: a fresh cargo run --release in /app/predictor with no predictions.csv present must read both CSVs, fit, and write the file itself. Dont leave results checked in, whatever is sitting at /app/predictions.csv gets cleared before that run. We also put the same program over another batch you have not seen, from a different welding cell with its own settings and its own training file, same format, where it has to come in under 22.0 per weld, so it has to fit from whatever is in /app/data when it runs, calls or a rule worked out once and written into the source are no use to us. Leave the two CSVs in /app/data exactly as they came, that export is what the inspectors signed off and we check it back against our copy. Keep everything you write under /app/predictor/src, because that and the two Cargo files are all we collect.

We get judged on what the calls cost us, not on how many we got right. /app/data/consequence_costs.csv is the contracts desk's table, what we pay when a weld that really had one finding gets called another, in pounds per weld. Shipping a cracked weld is a field failure and it dominates everything else on that table, pulling a sound weld costs us a scanner's morning. Averaged over the batch, what your calls add up to on that table has to come in under 20.0 per weld. The last model we were shown was right about four times in five and still came in at 26, because being right often is not the same as being wrong cheaply. A batch called as only one or two findings is not a classifier we can use, so across the batch it has to call at least three of the five. Every training file we hand it has all five findings in it, in its own proportions, so that is never the reason.
